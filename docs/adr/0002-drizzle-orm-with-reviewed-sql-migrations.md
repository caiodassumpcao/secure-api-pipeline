# 0002. Drizzle ORM with reviewed SQL migrations

- Status: Accepted
- Date: 2026-11-10

## Context

Data lives in PostgreSQL 17. The data layer has to:

- make injection structurally hard: values are always bound parameters;
- make tenant scoping explicit and reviewable — every query on tenant data filters by `workspace_id` (ADR-0005);
- keep schema changes visible in code review as the SQL that will actually run;
- support deployments where the previous application version keeps working against the new schema, so an app rollback never needs a database rollback (ADR-0008);
- provide typed queries and results;
- work with OpenTelemetry's PostgreSQL instrumentation (Phase 3).

## Decision

Use **Drizzle ORM** on the **node-postgres (`pg`)** driver, with **SQL migrations generated by drizzle-kit, reviewed and committed**.

- The schema is declared in TypeScript (`src/db/schema`); queries use Drizzle's typed builder, which always binds values as parameters.
- `drizzle-kit generate` writes plain SQL migration files. They are reviewed in the pull request like any other code — destructive statements in particular — and follow expand/contract.
- Migrations run as a separate one-shot step (the `migrate` Compose service, and before `docker compose up -d api` during deploys), never implicitly when the API starts.
- Repositories take `workspaceId` as a required argument. Raw SQL fragments (`sql.raw`) never receive user input; ESLint and Semgrep rules (Phase 4) enforce it.
- Phase 0 ships only the `pg` connection pool (`src/db/database.ts`) used by the readiness probe; Drizzle, the schema and the first migrations arrive in Phase 1.

## Alternatives considered

- **Prisma.** Productive, but its own schema language and generated client add an indirection between the code and the SQL that runs, and migrations are written in Prisma's DSL rather than reviewed SQL.
- **Kysely.** An excellent type-safe query builder, but it does not declare the schema or generate migrations, so migrations and table types would be maintained by hand.
- **TypeORM.** Relies on decorators (not erasable TypeScript syntax) and has a history of migration and typing pitfalls.
- **Raw `pg` + node-pg-migrate.** Maximum control and the fewest dependencies, but no typed queries and much more boilerplate in every repository.

## Consequences

- Queries read close to SQL and are parameterized by default; migrations are plain SQL in pull requests.
- Using `pg` keeps OpenTelemetry auto-instrumentation and pool metrics straightforward.
- Drizzle is pre-1.0: minor releases may change APIs. Versions are pinned and Dependabot updates are reviewed.
- Generated migrations are a starting point, not a guarantee: renames and destructive changes must be split into expand/contract steps by hand.
